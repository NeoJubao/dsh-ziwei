# 真太阳时可选、出生城市补全、没校正也能出报告

- 状态：已确认（Neo，2026-11-24，在 Plan mode 里确认了 Intent 和三处取舍）
- Issue：无
- 计划：[docs/plans/2026-11-24_solar-time-option-plan.md](../plans/2026-11-24_solar-time-option-plan.md)
- 前一份：[2026-11-19_v6-redesign.md](2026-11-19_v6-redesign.md)、[2026-11-20_v6-polish.md](2026-11-20_v6-polish.md)。本文件改掉其中的做法见 §4.1

## 1. Intent

- **要做什么**：
  1. 真太阳时校正变成每张盘各自的可选口径，和年界、月界、晚子时、闰月同级。
  2. 默认值看时间是怎么填的：直接选时辰（如卯时）就按这个时辰排，不校正；填钟表时间并填了城市才校正，确认那一步写明校正结果，可以一键改成不校正。
  3. 出生城市能认全部地级市、州、盟；填省名时说明范围太大，列出这个省的城市供点选。
  4. 盘没有校正（没填城市，或选了不校正）时，面板里的报告和速览照常写完，不再停下来要经度。
  5. 模型没写成报告、只回了一小段话时，报告页认得出来，给「重新生成」。
- **为什么**：2026-11-24 真机反馈。出生城市填了表里没有的地级市，也试了省名，都查不到经度；随后生成报告，模型两次只回了约 300 字要经度（`interpret-diag.log` 里 `mode=report`、`chars=321` 和 `291`）。反馈里的原话：「是否一定要真太阳时，应该做为一个可选设置项」。查的过程中还发现：时辰被记成整点钟表时间，补上城市后校正会把它往前推，部分日期排成前一个时辰的盘（§3.1 的表）。
- **约束**：
  - 禁区不变：不手改构建产物，不改 `package.json` 的 `name` / `private`，不碰 `~/.dsh/profiles/*`，不重启 DSH，不发布，不加 npm 依赖，只用黄金用例和它的合成变体。
  - `src/engine-core.js` 不动，已存的盘排出来的结果一张都不变。
  - 本机记录向后兼容：命盘库条目只在不校正时多一个 `settings.trueSolar: false`；命盘 key 的格式不变；1.6.0 和 2.0.0 写的记录原样可读。
  - Host 半（`index.js`、`src/ziwei-core.js`）要改，Neo 重启 DSH 后才生效；Client 半在旧 Host 上照常能用。
  - 城市经度来自 GeoNames（CC BY 4.0），入表之前先补 `THIRD_PARTY_NOTICES.md`。
- **不做什么**：县级和境外城市；生辰表单里按时辰选时间；DSH 会话里 `ziwei_paipan` 工具的参数和 agent 的追问规则；不 push、不发布。
- **成功指标**：
  - `node build.mjs && node verify/all.mjs` 全绿，`node verify/pack.mjs` 通过。
  - 选卯时并填城市，排出来的是卯时的盘。
  - 没校正的盘，发给模型的提示词里有「时间口径」一节，没有「经度 ≠120° 必做」。
  - Neo 重启 DSH 后在自己的盘上点「重新生成」，得到完整报告。

## 2. 用户故事

1. 作为只知道自己是卯时生的人，我选卯时，得到的就是卯时的盘，不管填没填城市。
2. 作为知道出生钟点和城市的人，我照旧得到校正后的盘，并且在确认那一步看到校正成了几点、哪个时辰。
3. 作为不用真太阳时这一派的人，我在确认那一步或生辰表单里关掉校正，这张盘以后都按钟表时间排。
4. 作为出生在地级市的人，我填自己的城市就能认；只填了省名时，我被告知要选到市，并且能直接点。
5. 作为没填城市的人，我点「生成报告」得到完整报告，报告开头有一句说明是按钟表时间排的。
6. 作为碰上模型只回了一小段话的人，我在报告页看到「没写成报告」和「重新生成」，而不是把这段话当成报告。

## 3. 验收标准

### 3.1 口径

- 当条目的 `settings.trueSolar === false` 时，系统应按钟表时间排盘，不管 `longitude` 填没填；`city` / `place` 照常保存和显示。
- 当条目没有 `settings.trueSolar`（或不是 `false`）时，系统应和现在一样：有经度就校正，没有就不校正。
- 不校正的盘和「同生辰、没填城市」的盘，命盘 key 应相同（它们是同一张盘）。
- 黄金用例的合成变体，06:00，男，经度 105.97：

| 日期 | 不校正 | 校正 |
|---|---|---|
| 1992-02-03 | 卯时，命宫戌 | 寅时（04:50），命宫亥 |
| 1992-05-03 | 卯时，命宫寅 | 卯时（05:07），命宫寅 |
| 1992-08-03 | 卯时，命宫巳 | 寅时（04:58），命宫午 |
| 1992-11-03 | 卯时，命宫申 | 卯时（05:20），命宫申 |

### 3.2 引导问答

- 当时间这一步答的是时辰时，排出的条目应带 `settings.trueSolar: false`；1992-02-03、卯时、男、经度 105.97 排出来是卯时、命宫戌。
- 当时间答的是时辰时，城市这一步的说明应改成「城市只作出生地记录」；填了城市的话，确认步应写明按这个时辰排、不做校正，并且没有校正开关（没填城市就没什么可校正的，不提）。
- 当时间答的是钟表时间并且填了城市时，确认步应总是写出校正后的时间和时辰，并给一个「不校正」的选项；点了之后说明换成按钟表时间排，选项换成「按真太阳时校正」，排出的条目带 `settings.trueSolar: false`。
- 当城市这一步答的是省名时，系统应留在这一步，说明范围太大，并把这个省的城市作为可点的选项；答对或换步后恢复常用城市。

### 3.3 生辰表单

- 「出生城市」下面应有单选组「真太阳时：校正 / 不校正」，有名字，在主区域。
- 选不校正时，城市下面的说明应改成按钟表时间排盘；保存的条目带 `settings.trueSolar: false`；改回校正时条目里不留这个字段。
- 填的是省名时，说明应提示填到市并举出这个省的几个城市，不给经度。

### 3.4 出生城市

- 城市表应包含 4 个直辖市、333 个地级市 / 州 / 盟 / 地区、没有上级地级单位的省直辖市（济源、仙桃、潜江、天门、神农架、石河子，以及海南的五指山、琼海、文昌、万宁、东方）、香港、澳门和台湾六市。
- v5 的 94 城经度应保持原值。
- 城市名在表里不应重复。
- 解析规则：
  - 以省名开头的，只在这个省里找；找不到是 `{ kind: 'province', province, cities }`。直辖市、港澳只有一个城市，直接是它。
  - 只写了省名而这个省有同名城市（吉林），按城市；写成「吉林省」按省。
  - 不以省名开头的，全表取最长的城市名，一样长取靠后的；一个城市都没有、但文本里有省名时按省。
  - 和别的省重名的州名（青海的海南）只在带着自己的省时才认。
- 用例：`泸州`、`四川泸州`、`四川省内江市`、`凉山`、`延边` 是城市；`四川`、`海南`、`吉林省` 是省；`北京朝阳` 是北京；`辽宁朝阳` 是朝阳；`青海海南` 是海南州；`吉林长春`、`四川成都`、`北京市`、`吉林` 和现在一样。

### 3.5 盘面

- 中宫的「真太阳时」应有三种写法：校正后的时间；`未校正`（没填城市）；`不校正`（选了不校正）。

### 3.6 提示词

- 当命盘文本写着「真太阳时: 未校正」时，`buildRequest` 的 system 应多一节「时间口径」，说明这是命主确认过的口径、不要追问出生地或经度、不要拒绝或中止；报告模式的自检清单里不应再有「经度 ≠120° 必做」。
- 报告和速览（一次性生成）应多一句：命主在这里无法回答追问，有疑点写进正文后照常写完。定向问答不加。
- 当命盘已校正时，`buildRequest` 三种模式的输出应和改动前逐字相同。
- `Core.PERSONA`、`Core.SELFCHECK` 的导出值不变。
- 交给新会话的首条消息：命盘未校正时不再把「缺少经度」列为疑点，并说明未校正是选定的口径。

### 3.7 报告页

- 当报告状态是完成、正文不到 1500 字、没有 `## ` 开头的行时，报告页应在正文上方提示没写成报告，并给「重新生成」。
- 正常的报告不出现这条提示；正在写、出错的报告走原来的分支。

## 4. 设计决定

### 4.1 和前面的 spec 不一样的地方

- v6 spec §3.2「填了出生城市、真太阳时校正让时辰换了：确认步明说」改成：填了城市并校正时总是写出校正结果（时辰换了的说法不变）。
- v6 spec 把城市表定为「和 v5 逐城一致」。现在是 v5 的 94 城一致，另外新增。

### 4.2 模块和接口

- `src/ui/20-util.js`：`CITY_TABLE`（省 → 城市 → 经度）；`CITY_LON` / `CITY_NAMES` 由它派生；`parseBirthplace` 多一个 `province` 结果，城市结果多一个 `province` 字段。
- `src/ui/21-storage.js`：`effectiveLongitude(input)`，`readingKeyOf` 和 `defaultChartName` 用它。
- `src/ui/26-store.js`：`storeEngineInput` 用它。
- `src/ui/23-birth.js`：`parseBirthTime` 的时辰结果在顶层带 `shichen: true`（`value` 仍是 `{ h, m }`，形状不变）。
- `src/ui/62-onboarding.js`：`data.solar`（`{ value: false }` 表示用户关掉了校正）、reducer 的 `setSolar`、状态里的 `province`。
- `src/ui/64-sheets.js`、`70-chart.js`、`85-reportview.js`：界面。
- `src/ziwei-core.js` 的 `buildRequest`、`index.js` 的 `handoffPrompt`：提示词。

### 4.3 数据

- 命盘库条目：`input.settings.trueSolar`，只有 `false` 一个取值，校正时不写这个字段。
- 命盘 key：格式不变。不校正时经度那一段是空的。
- 城市经度：GeoNames `CN` / `TW` 导出，取各地级单位驻地，0.1°。v5 已有的城市保持原值（和 GeoNames 的差都在 0.2° 以内）。

### 4.4 关键决定

- 口径放在每张盘上，不做全局开关：全局开关一拨，已存的盘全部重排，原来的对话和报告就对不上了。
- 不改引擎：不校正就是不把经度交给引擎。
- 提示词按命盘文本里的「未校正」判断，不靠 Client 多传字段：旧 Client 配新 Host 也能生效。

## 5. 测试决定

- 在这些接口上测：`ZWUi.parseBirthplace`、`ZWUi.readingKeyOf` / `effectiveLongitude`、`ZWUi.onboarding`（`reduce`、`inputOf`、`confirmModel`、`finish`、`OnboardingTalk`）、生辰表单组件、store 的 `chartOf`、`ZWCore.buildRequest`、中宫组件、报告页组件。
- 参照 `verify/ui-v6-storage.mjs`、`ui-v6-onboarding.mjs`、`ui-v6-chart.mjs`、`ui-v6-reportview.mjs`、`verify.mjs` 里已有的同类自检，新断言加进这些脚本。
- 期望值用上面表里的数和 GeoNames 的值，不在测试里重算。

## 6. 不在范围内

- 县级城市、境外城市、重庆等大市内部的经度差。
- 已存的「选时辰 + 填城市」的盘不自动改成不校正（记录里看不出当时填的是时辰）；要改到生辰表单里拨开关。
- 历史对话（另一份 spec：`2026-11-24_chat-history.md`）。
